## Candidate findings

- **L4-1** Concurrent requests for one uncached interface each send their own fetch (no in-flight dedup). Within one JS `Promise.all` / Python `gather`, N calls to a cold canister take N call slots + N fetch slots and send N identical fetches; a batch of 13 calls succeeds when the interface is cached and fails with a policy violation when it is not. Across concurrent requests (scripts or searches), every in-flight request repeats the fetch messages and their audit entries until the first reply fills the cache.
- **L4-2** One call-cap slot can send two messages (fetch fallback), so a run can send up to 2x `max_calls_per_script` messages and its audit `calls` can exceed the configured cap.
- **L4-3** `MAX_SEARCHES` is enforced only in the update path: the same batch of searches gets all answers from the query and 5 answers + errors once upgraded (one cold interface, or `certified_reads`); a cold search at position 6+ is never fetched.
- **L4-4** Searches take no run slot, so concurrent searches suspended on interface fetches are not bounded by `MAX_CONCURRENT_RUNS` and are invisible in `active_runs` (they do appear in `pending_run_ids`).
- **L4-5** A run slot is held across an unbounded-wait call; 8 runs waiting on a target that never replies make every later script "busy" until those calls return (symptom of register #44's root cause, new consequence).
